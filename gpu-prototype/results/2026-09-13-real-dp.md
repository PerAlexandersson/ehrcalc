# Real flagged-Kostka GPU comparisons on RX 9070 XT

Date: 2026-09-13

Hardware: AMD Radeon RX 9070 XT (`gfx1201`, 16 GiB) on Euler.

Software: ROCm 7.2.4 userspace container, rocPRIM 4.2.0, and `hipcc -O3
--offload-arch=gfx1201`. The host graphics driver was not replaced. Rust
release builds used the external Cargo target directory
`/mnt/2TB-Babel/ai-storage/cargo-target`.

## End-to-end variants

The CPU-enumerated hybrid materializes transitions serially, uploads each
layer, and performs only aggregation on the GPU. The GPU-resident version uses
one thread per source state to count and emit horizontal-strip extensions, a
rocPRIM exclusive scan for offsets, and rocPRIM sort/reduce. States remain on
the device between labels.

| Dilation | CPU packed modular wall | CPU-enumerated hybrid | GPU-resident device/total | Container wall | Result |
|---:|---:|---:|---:|---:|---|
| 1 | <0.01 s | 0.213 s internal | 0.023/0.028 s | 0.50 s | exact residue 125,835 |
| 3 | <0.01 s | not run | 0.122/0.128 s | 0.56 s | exact residue 369,110,195 |
| 6 | 1.27 s | 2.022 s internal | 1.183/1.194 s | 1.63 s | exact residue 306,879,955 |
| 9 | 48.86 s | 67.676 s internal | 12.914/12.929 s | 13.37 s | exact residue 2,040,897,519 |

The useful comparison at dilation 9 is 48.86 / 12.929 = **3.78x** for the
algorithm-internal end-to-end times, or 48.86 / 13.37 = **3.65x** including a
fresh Docker process. The hybrid loses because its serial transition
materialization alone takes 66.628 seconds; its GPU aggregation work is only
0.547 seconds.

The dilation-9 resident run reached 243,369 states and 115,666,316 transitions
in its largest layer. At that layer the six full-sized key/value arrays require
about 6.94 GB and rocPRIM reported a 2.33 GB sort workspace, for roughly 9.27
GB before small state and scan buffers. This fits the 16 GiB card without
chunking. The largest layers are dominated by the count and emit kernels;
sorting is no longer the limiting phase.

## Optimized resident kernel

A second optimization pass kept the recurrence and output unchanged while
changing four implementation details:

1. Count bounded compositions by a small per-state dynamic program instead of
   enumerating every extension a first time.
2. Maintain suffix capacity sums and begin each DFS choice at the smallest
   feasible value, avoiding branches that cannot fill the remaining strip.
3. Store the selected/next DFS choice in one array and launch 128-thread
   blocks. The measured build used 32-bit scan offsets under the configured
   transition cap; the subsequent safety fix uses 64-bit counts and offsets.
4. Sort only the occupied packed-key bits and reuse raw transition buffers as
   reduce-by-key output, removing two peak-sized allocations.

The suffix-capacity change is decisive. It reduces the large-layer emit work
from seconds to tens or hundreds of milliseconds, while the composition DP
reduces transition counting to well below one millisecond on every large
layer. All state counts, transition counts, and residues remain identical.

| Variant at dilation 9 | Residue lanes | Device work | Internal total | CPU/total |
|---|---:|---:|---:|---:|
| Packed CPU modular, before pruning | 1 | — | 48.86 s | 0.26x |
| Packed CPU modular, suffix-pruned | 1 | — | 12.74 s | 1.00x |
| Initial GPU-resident | 1 | 12.914 s | 12.929 s | 0.99x |
| DP count + reduced buffers | 1 | 7.673 s | 7.683 s | 1.66x |
| Feasible-suffix DFS | 1 | 0.653 s | 0.663 s cold | 19.22x |
| Final exact resident | 3 | 0.525 s warm | 0.640 s warm median | 19.91x |

The final three-lane result is
`[2040897519, 564828415, 700106644]` modulo
`[2147483647, 2147483629, 2147483587]`. Bounded CRT reconstructs the complete
stored integer `549126938733237505207`. Three lanes add only modest device work
over one lane because transition enumeration is shared.

For dilation 6, a three-lane 128-thread run takes about 0.092 seconds of device
work and 0.099 seconds internally, versus 1.27 seconds for the one-lane packed
CPU reference. Only two primes are required to certify its stored exact count.

After buffer reuse, the peak three-lane dilation-9 arrays occupy approximately
9.75 GB: 3.70 GB for raw/sorted keys, 2.78 GB for raw/sorted values, and 3.27
GB of rocPRIM sort workspace. This remains below the planned 14 GiB ceiling.

Five consecutive three-lane runs returned identical residues. Warm device work
was approximately 0.53 seconds; total timing varies by roughly 0.1 seconds as
the synchronous ROCm allocator and process context warm up.

The 0.640-second measurement predates the 64-bit scan-offset safety fix. Its
largest observed transition total was 115,666,316, so the recorded run itself
did not approach 32-bit wraparound and its result remains valid. The current
64-bit source compiles successfully without exposing GPU devices, but it has not
been benchmarked on the card because GPU execution was stopped after the display
fault described below. The 12.74-second CPU measurement uses the same
feasible-suffix pruning now present in both the packed modular reference and the
maintained `BigUint` streaming enumerators.

## Independent residue and validation checks

The resident binary accepts one or more runtime moduli, matching the compiled
lane count. At dilation 6 it matched the Rust reference independently under the
first two default primes:

| Modulus | CPU residue | GPU residue |
|---:|---:|---:|
| 2,147,483,647 | 306,879,955 | 306,879,955 |
| 2,147,483,629 | 1,629,530,989 | 1,629,530,989 |

Their product exceeds the stored exact dilation-6 count, and these two residues
reconstruct 157,798,415,095,915,566 by CRT. Three simultaneous dilation-9
residues reconstruct the complete stored count shown above. In addition, every
state count and transition count in the tested real layers matches the Rust
trace.

`gpu-prototype/run-smoke.sh` covers two moduli on small skew, flagged, and
zero-strip examples. Rust separately tests exhaustive small skew counts,
flagged counts, layer sort/reduction, coprimality rejection, packing width, and
bounded CRT ambiguity rejection.
`gpu-prototype/run-host-tests.sh` additionally checks transition totals beyond
`u32`, empty-frontier classification, and rejection of malformed or overflowing
numeric arguments without opening the GPU devices.

## Current boundary

This is a testable proof of concept, not yet Ehrcalc's production exact backend.

- The HIP source supports compile-time residue lanes; the exact driver batches
  up to three per pass. Four to eight simultaneous lanes are intentionally not
  used until their peak memory is measured on a non-display GPU.
- Strict/interior flagged counting is not implemented in the packed modular or
  HIP paths yet.
- A layer that exceeds the configured transition cap aborts cleanly; chunked
  aggregation is not implemented.
- Transition scan offsets are 64-bit even though the configured cap remains
  below `2^32-1`; this prevents a large sum of individually valid per-state
  fanouts from wrapping before the cap check.
- The executable targets `gfx1201` in the documented build command and has not
  been portability-tested on another AMD architecture.
- A `hipMallocAsync`/memory-pool experiment caused a GPU page fault and wedged
  Euler's display until suspend/resume. It was removed. Only the verified
  synchronous allocation path should be used on this display-attached GPU.
- The production Rust API and CLI still use the maintained `BigUint` backend.

The optimized result greatly exceeds the planned 3x large-case performance
gate. Strict/interior parity and production integration are the next useful
steps; further allocator or high-lane tuning should happen on a GPU not driving
the desktop.
